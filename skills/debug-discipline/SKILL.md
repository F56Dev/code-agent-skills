# Debug Discipline — 调试纪律（journal + gate + IIC 独立调查）

主开发模型调试时最大的风险是**盲目推进**：改了很多轮、每轮都觉得"这次能成"，实际在同一假设上打转。本 skill 用三个机制根治：**Debug Journal（外部化计数与复盘）、gate（无确认根因不改码）、IIC（独立调查破锚定）**。

## 调试流程（强制顺序）

```
收到 bug / 测试失败
  → ① 写复现测试（最小化，RED）
  → ② 开始 Debug Journal
  → ③ 形成第一个假设（写进 journal）
  → ④ GATE：假设未被判别性证据确认前，禁止改代码
  → ⑤ 确认根因 → 改码 → 验证 → journal 记录
  → ⑥ 若失败：journal 记录失败证据 → 第 2 次失败或僵局 → 委派 IIC
```

## ① 复现测试先行

- 先写**最小化**复现测试（不是整个场景），精确复现用户描述
- 复现测试失败（RED）确认 bug 存在后，才进入分析
- 无法复现 → 向用户提问（参数/操作序列），不要猜测

## ② Debug Journal（关键机制）

调试开始就开一份 journal（如 `temp/debug-journal-<bug>.md`），**每轮尝试都记录**：

```
## 第 N 次尝试
- 假设：<根因假设>
- 改动：<改了哪里>
- 预期结果：<如果假设对，应看到什么>
- 实际结果：<测试输出/日志>
- 失败原因判定：<假设错误 / 改动没对准 / 证据不足就动手>
- 症状还是根因：<这次改的是症状还是根因>
```

**journal 的作用**：
- **计数看得见**：第 2 次失败在哪一目了然，不靠记忆
- **强制减速**：写 journal 占用一步，阻断"连改"
- **打断锚定**：重读 journal 看到"第 1 次就想改这里失败了"——阻止重复
- **给 IIC 素材**：异族模型读 journal 才能发现你锚定在哪个错误前提

## ③④ GATE：根因确认前不改码

- **每轮只测一个假设**，且必须先在 journal 写清楚假设 + 预期结果
- 无假设的修改 = 违规
- **根因未被判别性证据确认前，禁止改代码**。判别性证据 = 能区分"这个假设对/那个假设对"的日志或测试
- 改的是"症状"还是"根因"？回答不了就先不要改

## ⑥ 第 2 次失败或僵局 → 委派 IIC

当第 2 次修复失败，或调试陷入僵局（改了多轮无进展）时，**强制停下**，委派 IIC：

```
task(
  subagent_type: "iic",
  description: "IIC investigate <bug>",
  prompt: "请独立调查 bug：<描述>。
  - 项目根目录：<绝对路径>
  - 复现测试：<绝对路径>
  - Debug Journal：<绝对路径>
  - 宪法文档：<绝对路径>（如 PRD/architecture/detailed-design）
  请按 IIC 流程：亲自复现 → 审查 journal → 独立根因分析 → 判别性验证步骤 → 候选修复方向。
  你不改代码，验证步骤由我执行。"
)
```

- IIC 返回后，**执行它的验证步骤**，把结果写回 journal
- 验证确认它的假设 → 主 agent 实施修复（代码归主 agent）
- 验证证伪 → 携新证据回 IIC（R2），仍未一致 → R3 升人工
- IIC 是"调查"，你（主 agent）是"实施"——**调查权与实施权分离**，这是核心纪律

## 硬性检查

- 调试中每次改码前：journal 里有假设吗？根因确认了吗？
- 第 2 次失败：我是不是应该停下委派 IIC 而不是继续改？
- 声称"修好了"前：复现测试 GREEN 了吗？journal 里有失败证据和最终根因吗？

## 注意

- Debug Journal 在调试中是**工作产物**（消费即弃），不触发 docs-review；**修完后**才正式化为 post-mortem / BUG-LEDGER 条目
- IIC 报告是工作产物，消费即弃，不触发 docs-review
- 不要把 IIC 当"第二个主 agent"——它只调查提方案，不改码；改动全在你
- 若 IIC 幻觉（无证据断言），在回环里点出并附证据
